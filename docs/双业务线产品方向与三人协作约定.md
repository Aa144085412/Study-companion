# 双业务线产品方向与三人协作约定

生效日期：2026-10-23。维护对象：全体开发者及其使用的 AI 编码助手。

本文是新增的产品规划与职责约定，不修改现有任务编号、任务负责人或分支安排，也不代表以下能力已经实现。本文中的A/B/C指产品职责角色；现有任务文档中的工作者A/B是执行者称呼，两者不自动对应。实施前由团队明确对应人员；现有任务状态、暂停条件和进入检查继续有效。当前实现以代码、CONTEXT.md和TASKS.md为准。

## 1. 两条业务线，一个共享底层

| 业务线 | 服务对象 | 首阶段目标 | 不作出的承诺 |
| --- | --- | --- | --- |
| 家庭学习 | 首批海淀学生家长及孩子；架构不绑定地区、年级或学科 | 将网课中的PPT/文档与讲解整理成可溯源的学习笔记，支持复习与证据充分的练习 | 不将答对选择题等同于掌握，不承诺提分或代替教师判断 |
| 工作与科研 | 公司员工、高管、科研人员 | 整理PPT演示、文献分享、组会汇报、培训和会议材料，快速回看原文与原视频 | 不把模型推测当会议决议，不承诺自动理解全部实验操作或仪器画面 |

两个入口共享导入、媒体、转写、OCR、证据、审计、版本及导出能力。业务差异放在输出结构、提示词配置及交互层。首阶段不拆成两个独立仓库或复制两套处理管线；是否拆分部署以后按实际交付需要评估。

## 2. 稳定性优先及首版输入范围

1. 优先完成“本地视频或课程材料 → PPT/文档OCR + 讲解ASR + 可用字幕 → 时间对齐 → 有依据的笔记 → 一键回看片段”的闭环。
2. 保留本地视频导入，包括用户用JiJiDown下载后导入。B站文献分享、组会汇报等适合作为公开测试素材；网页下载不可成为唯一入口。
3. 首批重点覆盖课件清晰、讲解相对单一的录播内容。复杂多人会议、说话人身份识别、实时录音/直播作为独立后续能力，不因“会议端”命名就宣称已经支持。
4. 实验实拍、手势动作、仪器型号/状态/孤立读数不作为首版可靠能力。已有相关代码保留，但不能仅凭VLM推测进入确定事实、标准参数或题库。
5. PPT图表、公式、上下标和单位也可能误识。无法可靠读取时保留时间位置并提示回看；不得将“画面像PPT”直接等同于高可信事实。
6. 不为单个学科写死错词替换、结论或参数；通用格式/噪声规则应记录适用条件与误判边界。

## 3. 共享证据与生成规则

- 原始ASR、OCR、字幕与模型推断分开保存，带来源ID、媒体ID、时间范围、页/帧位置（可取得时）及版本。修正候选不得覆盖原文。
- 引用可定位不等于结论正确。审计须核对主体、步骤、条件、否定、因果、数值单位、比较基线及适用范围。
- 长内容采用分批提取和全局合并；禁止直接拼接批次摘要。冲突保留并显式标注，不静默选一个答案。
- 同一笔记条目显示一个依据入口，展开保留所有支持片段；不同媒体或相隔较远的证据不得伪装成一个连续片段。
- 笔记、来源或模型变更必须可追踪；重生成保存新版本，保留旧笔记和人工修改。不得手改store.json替代迁移/保存接口。
- 尚无充分证据的内容归入待核对；不得为满足笔记长度或题目数量降低门禁。

## 4. 家庭学习端要求

- 以课程知识点、解释、适用条件、常见疑问、原片定位组织笔记；年龄/难度由用户配置，不硬编码为某一年级。
- 练习只使用已通过准入的知识，不从原始噪声字幕直接出题。优先步骤目的、概念辨析和判断依据；题目不足时如实提示。
- 家长反馈区分“观看/完成”“答题表现”“待复习项”；不能由模型评分宣称孩子已掌握或进行能力诊断。
- 首阶段延续少量家庭、本地安装私测。多账号、家长/孩子权限、跨设备同步若未实现，不展示为已经可用。

## 5. 工作与科研会议端要求

默认输出结构：主题与摘要、按议题整理的要点、明确结论/决议、行动项、争议与待确认项、证据索引。

- 单向报告可以没有决议和行动项；空字段显示“材料未明确提及”，禁止为了填满模板编造。
- 严格区分讲者观点、引用文献结论、会议共同决定、模型整理建议。报告中的“建议”不能自动升级为团队决定。
- 行动项仅在来源明确时填写任务、责任人、截止日期；未明确的字段留空并标待确认。不能从参会名单猜负责人，不能把“下次讨论”推算成具体日期。
- 科研笔记区分研究问题、方法概述、结果、局限与讨论。文献标题/作者/年份/DOI未读取到时不补造；未经外部核验不标为已核实引用。
- 会议笔记不是可直接执行的湿实验SOP；视频中的单次条件不能自动迁移为用户项目的标准操作。
- 模型不自动发送纪要、分配任务或对外承诺；发送与共享必须由用户明确触发。

## 6. 模型适配与降级

- A、B可以配置各自的模型和API，并负责本板块的效果验证。共用配置/适配接口和证据门禁，不要求共用账号、密钥或同一个模型；API接入本身不是C的专属工作。不得绕过证据门禁直接生成“已确认”正文。
- 分别记录转写、OCR/视觉、结构化提取、语义审计的模型/版本、能力测试结果及运行配置。能连通接口不等于能力合格。
- 至少区分：仅文字整理、文字+OCR联合整理、通过专项验证的视觉增强。视觉增强默认不能用来确认仪器或实验动作。
- 某能力不可用时，保留原资料并说明当前仅用了哪些输入。缺OCR不能假装已看懂课件；模型超时/JSON无效不能保存为成功笔记。
- 失败要可重试，成功阶段按输入/模型/提示词版本缓存；不得重试导致重复笔记或丢失已保存内容。
- 禁止静默切换云端。云端模型/语音服务的数据流向须在使用前明确告知；现有edge-tts为云端，不得宣传整套产品完全离线。
- 新增或切换模型须跑对应能力回归；高配置模型通过不能代表低配置模型通过。

## 7. 三人职责与接口边界

A、B由两位协作者分别负责，具体账号待团队填写；C由项目发起人负责。C是产品统筹、公共基础设施与发布交付负责人，不是第三条业务线，也不是所有剩余开发工作的默认负责人。

| 角色 | 必须交付 | 自己承担的质量责任 |
| --- | --- | --- |
| A 家庭学习端 | 家庭端完整流程、学习笔记/练习/家长反馈、相关模型配置与业务评估 | 本板块功能测试、场景验收、用户反馈和缺陷修复 |
| B 工作与科研端 | 报告/会议模板、议题/行动项交互、相关模型配置与业务评估 | 本板块功能测试、来源正确性检查、用户反馈和缺陷修复 |
| C 产品统筹与交付 | 版本范围和优先级、公共配置与数据约定、开发环境与自动检查、集成版本、安装更新/回滚说明、试用安排 | 公共改动兼容性、集成与发布检查；协调公共缺陷负责人，不包办两端测试 |

### C的具体工作与交付物

| 工作 | 可检查的交付物 | 不应重复做的工作 |
| --- | --- | --- |
| 需求与版本规划 | 每个两周迭代的目标、必做/不做清单、负责人、依赖和验收方式 | 不代替A/B设计所有业务交互 |
| 公共配置与模型设置 | API地址/密钥/模型选择的统一配置约定、连接检测、超时与错误语义；示例配置不含密钥 | 不替每个人购买API或独自调试所有模型提示词 |
| 数据与文件管理 | 视频/资料/笔记公共结构、导出备份恢复约定、版本迁移和回滚办法 | 不直接修改真实用户store修补演示效果 |
| 开发环境与协作 | 新克隆启动说明、依赖清单、合成样例、一条基础检查命令、共享接口清单、PR自动检查 | 不要求协作者复制发起人的私人数据或绝对路径 |
| 集成与发布 | 两端集成验证记录、可启动的试用包、版本说明、升级及回退说明 | 不在业务功能未经作者自测时替其兜底验收 |
| 试用与反馈 | 试用任务、反馈记录及优先级；将问题分派给具体负责人 | 不以个人感觉替代用户任务验证 |

已有导入、ASR/OCR、时间对齐与溯源能力作为共享资产复用，不把它们重新实现一遍作为C的新任务。需要公共修复时由团队认领；A/B可以提交修复PR，C协调接口兼容与合并顺序。

### 决策与协作边界

- 普通业务界面、模板、提示词和内部实现由A/B在已约定范围内推进，不必每次等C批准；仍须通过相应测试和PR复核。
- 改公共API/Schema、存储迁移、默认模型或外部数据流向、安装依赖及发布范围，先由C协调受影响负责人，记录影响与兼容方案。
- 每个缺陷只有一个明确实施负责人。谁的改动引入回归，谁先负责定位和修复；不以“涉及底层”为由自动转交C。
- A/B的PR必须附自测及场景验证；跨角色改动至少另一位开发者复核。C提交的公共改动同样需要他人复核，不能自我豁免。
- 公共接口未就绪时，先约定版本、输入输出示例、错误码和固定测试数据，使两端可以独立开发。真实凭据不进入示例。
- 当前server.mjs和public/app.js仍承载多种职责，职责表不代表目录已拆分。共享文件修改先登记范围、协调合并顺序；小步拆分，禁止一次性重写全部功能。

## 8. 合并与验收要求

- 每人独立克隆/工作区及分支；禁止多人同时对同一工作树切分支、重置或启动共享同一数据目录的服务。
- 用小PR合并，说明问题、变更、测试、模型配置、已知限制和回滚方式。禁止force push覆盖他人提交。
- main只接收完成相关验证的代码。GitHub分支保护、强制审查/CI需单独配置；本文不代表它们已经启用。
- 公共管线变更至少回归两条业务线。只改文档时检查链接和一致性，不要求无关模型全量重跑。
- 首阶段发布必须覆盖：原文件/视频回放、来源跳转、长材料覆盖、保存恢复、重复操作、超时重试、缺能力降级、历史版本兼容；失败不得静默丢数据。
- 内容评估保留未参与提示词调试的素材，分别记录错误接受、错误拒绝、遗漏、引用定位误差、耗时和失败率；不将字符串引用匹配率或单元测试通过率称为内容准确率。
- 至少覆盖文字PPT、含图表/公式PPT、低清晰度/噪声音频三类输入，并覆盖每个宣称支持的模型配置。低质量输入允许拒绝，但必须明确告知。
- 对外宣称前，人工复核中发现的未解决关键错误（错误决议/责任人/截止日期、改变结论的数字或否定含义、误导性实验参数）必须修复或隔离，不能留在确认正文中。
- 发布验收记录样本数量、材料类型、人工核对方式与未通过项；当前仍是研发原型，不因新增入口或模板就称为产品级。

## 9. 数据与开发素材

家庭资料、企业录音、未发表科研材料、cookie、密钥、模型文件和本地学习库不得提交到Git。回归素材使用有权使用的公开材料或去标识合成数据；公开链接不代表有权再分发整段视频。

默认本地处理与现有本地私测方式保持一致。对外模型、共享和导出行为需明确可见；数据删除/恢复能力与限制如实说明。

## 10. 近期执行顺序

1. C组织一份两周版本清单：A/B各交付一个完整使用流程，C交付公共依赖及集成版本；明确必做、不做、负责人、验收与依赖。
2. C优先补齐“新协作者拉下代码即可开发”：可复制的启动说明、示例配置、无隐私测试素材、基础检查命令；用新目录验证，禁止依赖个人机器绝对路径。A/B各自实际试跑并反馈。
3. C建立PR基础自动检查及试用版本产出流程；A/B负责自己的业务测试，共同完成合并后的双端回归。分支保护、CI和安装包在实际完成前保持待办状态。
4. A/B分别提供课程、文献分享/组会样例与人工检查记录，C协调统一评估格式及模型能力矩阵；不重复建设现有导入/OCR管线。
5. C组织少量用户试用并排优先级，A/B处理对应业务反馈；公共问题明确认领后修复。
6. 实验视觉、复杂仪器、实时多人会议与自动说话人身份识别，另立专项验收后再开放。

每轮完成标准是“具体交付物 + 可复现检查 + 已知限制 + 负责人的修复闭环”，不是所有问题都由C检查一遍。当前未配置的自动化、安装更新能力仍是目标，不是现有产品事实。
