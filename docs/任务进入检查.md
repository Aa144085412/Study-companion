# 每次执行前的任务进入检查

适用于 A、B、真人协作者和其他执行者，每次新任务、恢复旧任务或更换执行者都要执行。以原始主项目 origin/main 的代码、TASKS.md、CONTEXT.md 和 COLLAB.md 为依据；任务分支说明是补充，不能把分支完成或旧聊天当作主项目已经集成。

## 固定执行顺序

1. 在自己的项目目录检查 `git status --short --branch`，确认未提交文件的归属；执行 `git fetch origin`、`git log --oneline -15`。先检查与 origin/main 的差异；需要同步时提交已有工作并合并主线，不强推、不清理他人文件。
2. 读取 CONTEXT.md 顶部最新状态、完整 TASKS.md 和 COLLAB.md。任务可能在文件末尾；历史 Recovery Capsule 只作背景。查看所有 open/doing/blocked、暂停条件及已完成条目中的“未验收/后续/遗留”，不能只读标题或顶部。
3. 运行 `npm.cmd run task:check`。查找交接文件中未登记的任务、重复编号、未指定负责人和分支成果尚未集成等情况，再阅读 [主项目核查与分工](主项目核查与分工-2026-10-23.md)。已有台账仍要按本轮代码和远端变化复核，不能复制上次的“通过”。
4. 明确本阶段对应的原任务、负责人、分支、涉及文件、验收与条件。已完成任务不要重复实现；未完成的验收另列子阶段；暂停任务不得因 status=open 自动恢复。其他人正在做的任务先避开或协调。
5. 在 `docs/任务进入记录/` 写本次 Markdown 记录，列出基线、核查发现、遗留处理、原框架、认领和验证计划。将 TASKS.md 中本任务改为 doing 并填写准确 owner，再运行带任务与 owner 的检查，确认允许进入后开始实现。
6. 完成后运行相关验证，更新同一进入记录、TASKS.md、CONTEXT.md 和 A/B 分工；只提交具体文件，按授权上传并核对远端与 PR。区分本地提交、已推送、检查通过和已进入 main。发现遗漏要登记负责人、依赖与下一步，不能只在聊天中提及。

在 Windows PowerShell 的项目目录，认领后的检查示例为：

```powershell
npm.cmd run task:check -- --task T57 --owner "工作者A/Codex"
```

T57完成后该示例会被拒绝；下一位应填写自己真正认领且状态为doing的任务。命令只读本地文件和Git，不联网、不自动认领、不修改任务，也不读取用户笔记或密钥。它无法判断内容准确性或替执行者阅读全部遗留事项；执行前的fetch与Markdown记录仍需实际完成。

## 框架优先级

沿用主项目原生 Node HTTP 服务 `server.mjs`、`public/` 中文界面、Python/Pydantic 契约，以及 `src/pipeline/` 编排的 evidence_cleaner → note_synthesizer → attribution_auditor → note_renderer → quiz_engine 五阶段流程。优先补原任务已有实现、验证和文档，不为了新分工另建一套业务框架。需要改变框架时，先记录问题、与原实现关系、迁移影响，再按用户授权处理。

PR #1中的云端 API 和统一工程检查仍需单独审阅、集成；分支里通过测试不代表当前main已经具备这些功能。每次开工重新确认其实际状态，不硬套本次基线。

## 进入记录模板

```text
日期 / 工作者 / 原任务与本阶段：
当前分支 / 已获取的 origin/main SHA / 远端核对结果：
工作区归属 / 本轮读过的进度与原框架文件：
原任务遗留 / 状态冲突 / 本阶段如何处理或转交：
负责人 / 涉及文件 / 暂停或外部条件：
验证计划 / 实际命令、环境与结果：
本地提交 / 远端分支 / PR / main集成状态：
A下一步 / B下一步：
```

本轮记录见 [T57进入与验收记录](任务进入记录/2026-10-23-T57.md)。这个规则由每位执行者遵守，不能仅因文档存在就声称每次检查已实际执行。
